## Autonomy：初始化失败及原因

会话开始与结束均记录：

```json
{
  "enabled": false,
  "coverage": {"state": "unavailable"},
  "counts": {"observation_errors": 1},
  "last_error": "install: AttributeError: get_multitasking_roll"
}
```

两个暂存缓冲的使用量与峰值均为 0，选择回调用时为 0。记录中有 **1,284 条来源为 `AUTONOMY` 的交互**，但 `autonomy.decision` 与关联决策均为 0。旧有的交互来源标记说明这些行为来自自主系统，不能补出候选、评分或抽取结果。

当前初始化先包装 `AutonomyComponent.get_multitasking_roll`，随后直接包装基础 `sims.sim.Sim` 的同名方法；缺失属性会使整个 Autonomy 初始化退出并撤销已装的入口。EA 的组件导出机制则把方法挂到 **`type(owner)`，即具体实例所属的类**，并在闭包中保存原组件函数。基础 Sim 类不保证拥有该方法，只包装组件本身也不保证能观测已经生成的转发函数。

本次从本机游戏 `simulation.zip` 读取并执行 `ComponentMetaclass.__new__` 中的原生 `build_exported_func` 和 `apply_component_methods`，在受控的基础类／子类上得到：

1. 导出后具体子类具有 `get_multitasking_roll`，基础类仍没有；对基础类安装现有 Hook 复现同一个 `AttributeError`。
2. 只包装组件类时，调用具体实例的方法会执行原 getter，但包装回调次数为 0，确认闭包保留了旧函数。
3. 包装具体子类的方法后，一次调用得到一次观测，原 getter 仍只执行一次，返回值相同。

这将故障定位到本次接入的类／时机假设，优先怀疑的是基础 Sim 包装步骤。实机日志未保存完整异常栈和具体实例类，因此这里区分日志直接证据与原生机制复现，没有声称捕获了实机的具体子类名称。

此前测试夹具预先在假的基础 Sim 类上定义了 getter，覆盖了“导出函数保留旧函数”的情形，却遗漏了“只挂在具体子类、基础类缺失”的情形。15 个原生符号核验也只证明组件等函数体存在，没有证明基础 Sim 上有动态导出的入口。这是此前 215 项离线测试未发现该问题的原因。

初始化失败被隔离，基础记录器和 Context 继续工作。本局不能验证 Top 5、评分组成、原概率、筛除原因、入队门槛、缓存关联、立即执行或真实采集开销。结束时 GSI 开关为开，不能据此判定本采集器成功运行，也不能从当前证据确定是谁开启了它。

计数基于原始日志中事件的最新版本以及 Context 导出，没有离线补写。相同资源、来源交互和导出历史可能重复出现，因此下列数字是**文本出现次数**，不是独立行为数或整体覆盖率。

## 修复优先级与下一次验收

1. **先修 Autonomy 初始化。** 接入实际实例类型上的导出方法并处理动态挂载时机；缺失入口应单独报告覆盖受限，避免可选入口使整套采集退出。增加基础类缺失、具体子类导出、类在初始化后出现等回归样本，同时继续验证不额外调用惰性 getter、不改变随机数调用次数。
2. **再处理隐藏聊天条目的分层与名称。** 保留真实内部决策，单纯聊天动画／监听步骤应按证据归入内部层；不要用看似通顺的猜测掩盖类型不匹配。
3. **区别实例状态描述与资源模板。** 排查物件名称字段可用时机，保留解锁资源的原始描述，不把解锁通知写成持有 Buff 的事实。

修复后的实机验收首先检查 `autonomy.coverage.state` 和 `last_error`，然后确认实际产生并关联 `autonomy.decision`；此后才能用真实候选检查每层最多五项、赢家保留、原概率、提交门槛与开销。本局可以继续用于行为历史和语义化分析，但无法事后还原当时未采到的 Autonomy 决策过程。
