# 首轮实现与验收

版本：v0.3。日期：2026-09-15。本页保存首轮目标与当前边界；0.6.0 事件扩展已完成源码与离线核验，按本轮决定交付试用，具体证据见[新报告](validation/2026-09-15-event-expansion.md)。此前[首轮实机证据](validation/2026-09-14-first-round.md)不能代表新版本已验证。模块范围见[总体设计](modular-context-provider.md)。

## 1. 首轮目标

在本地游戏中打通“指定目标当前状态 + 已观察历史 → 规范数据 → 可读表达 → 完整 JSON 输出”，并分别验证三个模块。

主要验收场景确定为做饭与吃饭：核对交互与目标物件、触发来源、饥饿值变化，以及实际发生的物件状态和 Buff 变化。另用小型社交场景核验关系变化，并覆盖同型号物件实例隔离、完成/取消/未知和换地块等边界。具体交互、字段及终态入口先核对源码，再用游戏行为核验。

事件记录从首轮纳入实现。旧 Experience 导入、长期记忆、任意时点状态重建、模型生成、复杂 UI 和游戏效果执行不作为前置条件。

### 已确认的首轮边界

| 项目 | 决策 |
| --- | --- |
| 交付 | 一个 MOD 内含三个模块；以游戏内查询及 JSON、中文导出完成开发验证 |
| 范围 | 当前地块内已实例化的 Sim 和物件；场外角色明确排除出首轮 |
| 事实 | 同时记录行为经过、状态变化和触发来源；可访问性与观测缺口分别表达 |
| 触发来源 | 区分玩家、自主选择、脚本/系统等，保留 EA 原始来源值和发起者/目标；首轮不采集候选评分或推断动机 |
| 状态 | 需求、Buff、关系及物件常用状态，逐项登记读取依据；不全面枚举隐藏内部字段 |
| 粒度 | 事件逐次记录，保存回调中可取得的前后值；当前连续数值通过 Context 按请求读取，不做定时历史采样或任意时点数值重建 |
| 事件层次 | 主要交互进入默认历史；内部步骤保存为调试观测，有明确身份依据时关联，按需展开 |
| 历史 | 日志落盘，按每次运行隔离；重启或读档开启新范围，暂不自动串联历史 |
| 中文 | 逐项、逐条解释，同原始数据对应；不生成活动回顾或叙事摘要 |
| 过载 | 内存、写入和采集错误暂停并明确报告；0.6.0 数量满改用 FIFO 并公开淘汰数，不再因数量上限暂停 |

角色或物件退出观测范围后停止采集其后续状态，已有历史保留并标记观测截止。换地块释放旧订阅并建立新的地块观测范围；未知或未经证实的跨加载连续性按独立运行范围处理。

## 2. 实现顺序

| 阶段 | 工作 | 退出条件 |
| --- | --- | --- |
| A：加载与最小读取 | 核对编译环境、构建包、安装目标和日志；增加一个最小调试入口，读取指定 Sim 与时间 | 游戏确认加载本项目，输出可定位的实体与时间；重复加载/换地块没有重复注册 |
| B：最小数据契约 | 用实际读取结果确定实体、时间、来源、事件、快照、可用性与版本；为模块准备最少样例 | 字段含义与范围可解释；示例不依赖旧 Experience 格式 |
| C：三个模块贯通 | 实现少量事件接入、查询组合、规则转换和文件导出 | 同一场景得到可追溯的原始事实与可读表达；独立关闭模块行为明确 |
| D：故障与范围验证 | 持久化、重复事件、实例隔离、未知结果及生命周期边界 | 声明范围内的验收通过，失败与未支持项都有记录 |

每个阶段只增加验收所需的辅助工具和测试。接口、词条与读取范围随真实数据核定，不能将本文示意能力标成已实现。

## 3. 共同验收标准

| 检查面 | 验收要求 |
| --- | --- |
| 来源与版本 | 每次结果可定位游戏版本、模块/规则版本及源码依据，记录本次 DLC/MOD 与场景范围 |
| 实体身份 | Sim、物件实例、资源定义不混淆；64 位身份经过 JSON/消费者后保持精确 |
| 一次发生 | 同一观测重复投递可去重；两次独立同名动作、两张同款物件不会误合并 |
| 状态与时间 | 当前值与直接查询相符；声明读取区间，历史时间和当前状态不混用 |
| 结果真实性 | 完成、取消、失败、未知/未闭合有证据；操作配置、取消请求不冒充实际后果 |
| 范围与缺失 | 未支持、读取错误、停用、空结果和截断明确；未完成必需项不能算成功 |
| 生命周期 | 换地块、对象卸载、重复注册及停止模块后行为可解释，不遗留重复订阅 |
| 存档与连续性 | 未验证跨运行连续性时明确隔离；读旧档后不把放弃的未来历史混入当前结果 |
| 持久化 | 已接收与已写入分开；失败不静默丢弃唯一记录；尾记录异常和重复重放可检测、处理 |
| 游戏行为 | 采集错误不改变原返回值、异常或游戏结果；对象访问时机正确，输出有界 |
| 语义表达 | 取消和未知不写成完成；缺词条保留原标识；文本可回到原始数据和规则版本 |
| 组合运行 | 仅事件记录、仅当前查询、仅离线语义化和三者全开均有明确输入/输出与能力状态 |

## 4. 验证方式与证据

纯数据逻辑使用新契约的合成样例验证身份、去重、时间、状态、规则和序列化。游戏接入使用受控操作与直接查询核对，不把同一个 Hook 的两份日志当作独立真值。

记录预期操作、实际结果、日志/输出位置、时间范围、失败项及采集缺口。对象和记录规模确定后测量查询耗时、读取区间、事件延迟、队列长度与文件增长，再制定预算；当前不虚构性能阈值。

静态定位、离线检查和游戏实测分开报告。没有启动游戏的检查不能写成游戏通过；旧原型的 13 项检查及旧参考项目的样本计数不代表新实现合格。

## 5. 实现结论与后续扩展

- 实际用户数据目录、Python 3.7 构建与脚本加载路径已核验，见[开发基线](reference-baseline.md)。
- 交互、状态、通知及注销入口、发送条件和版本边界已登记，见[接口依据](runtime-interfaces.md)。
- 使用 schema v1、模块/规则 0.1.0 和明确的常用状态目录；未支持字段与未解析名称显式标记。
- JSONL 日志、查询 JSON、缓存/队列预算和写入确认语义已实现，见[运行说明](runtime-usage.md)。
- 仅记录、仅当前查询、离线语义化、三模块全开与过载暂停的行为均有对应检查。
- 后续优先按真实使用需求扩充词条和状态目录，改善导出延迟，并针对其他 DLC/MOD 组合与长时负载单独验证。

需求、Buff、关系和物件常用状态均纳入首轮；具体支持项写入能力目录并分别验收。后续再扩充隐藏统计量、更多玩法字段及场外观测。新增能力继续按“需要什么事实—来自哪里—怎样验证—缺失怎样表达”登记。候选目录见[Context 分类](runtime-context-taxonomy.md)，后续玩法见[愿景资料](vision/README.md)。
