## 需要优先改进的问题

### 1. 技术事件大量进入主要历史

`commodity_SimInfo_TimeSinceLastSlept` 有 1871 条，`commodity_SimInfo_TimeSinceLastSocial` 有 757 条，两项共 **2628 条，占全部事件的 30.8%、直接数值效果的 73.7%**。均通过 StatisticSetMaxOp 重置。另有自主情绪计数器、冷却计时器等。

这不是本 MOD 恢复了定时采样，而是游戏在活动中反复执行真实数值操作，本 MOD 将它们逐次作为主要效果记录。当前“必须有操作来源”的条件保证了观测方式，却没有区分生活意义与内部记账。

交互也有相同问题：SocialObservation picker、被动坐着／睡眠、游戏垫 active/passive 等大量进入主要层。甚至已在 `profiles.py:32`、`:33` 明确解释为“进食内部步骤”的 Food_Eat_Active／Passive，仍有 40 条位于主要层。Buff 中常见的室内外检查、坐姿和隐藏情绪载体也在占位。

建议按已核验的类型、资源和调用用途建立分层规则：确认属于技术机制的进入 internal；有生活意义的社交动作保留主要层；未知用途继续保留可见。不要仅按 `visible=False` 一刀切，也不要为解决噪声重新引入连续值采样。分层改善可读性，但如果仍完整保存调试事实，它本身不会降低原始日志体积。

### 2. 序列化的类型与名字入口不正确

- **广播器误作物件。** 13 个广播事实的 payload.broadcaster 都被编码成 `object:<小整数>`，例如 `object:193`。`EventSources.scalar()` 先尝试实体解析，`EAAdapter.event_reference()` 又把所有有 `.id` 的对象当作游戏物件，最终给 Broadcaster 调用物件命名方法，产生 `〈未解析：0.ObjectName〉`。广播器身份、广播 tuning 与真实 `broadcasting_object` 应分别序列化。
- **情绪名称入口写错。** 64 条情绪通知都读取了 `mood_name`；EA 实际使用 `mood.mood_names[mood_intensity]`（`sims/sim.py:1855`）。当前输出“未配置显示名称”不能证明游戏没有中文名。事件还缺少旧、新强度；无法从本次日志补造旧强度。
- **配方与来源交互没有使用对应命名接口。** 8 个 recipe 通过没有名称属性的通用 resource 路径读取；EA Recipe 有 `get_recipe_name()`／`get_display_name()`（`crafting/recipe.py:492`、`:496`）。cause.source_tuning 也没有复用主交互已解析的名字。应优先修正类型适配器，再考虑词表扩充。

这类问题会影响下游对资源的理解，不能只替换显示文字掩盖。

### 3. “关联到此实体”与“效果作用于此实体”混在一起

记录器为支持发起者查询，会把 cause.actor 加入索引和 participants，这是合理的。但中文解释直接把全部 participants 拼成主语，没有按 roles 区分。

例如日志 1859 的受影响者为 Lila，Nyssa 被追加为 `initiator`，最终文本却是“Lila Landry、Nyssa Landry新增Buff……”。日志 1845 的社交需求效果也把受影响者与发起者并列。此类文本可能让下游以为同一个值或 Buff 同时作用于两人。

建议为数值、Buff、广播等明确记录 `subject/affected`，保留 `initiator`；中文模板按角色表达。实体索引继续包含所有相关实体，不能通过删去发起者来修显示。

### 4. 结果已采集，动作关联仍有缺口

3573 个效果有 `cause.event_id`，在最终事件表中全部能找到父事件，没有悬空引用。但 **8 条制作、5 条付款、2 条技能等级变化的 cause 都为 null**。22 条库存变化没有动作 ID，且 roles 全部为空；有的只有 ObjectCreationOp 操作来源。

库存样本已保留真实容器与物品、插入前后状态，例如同一本书从一个书架取出，后来进入另一个书柜。涉及纯物件容器时，历史未保留操作者，因此按 Sim 查询可能无法看到该次搬动；不能回答“是谁放进去的”。

建议核对制作阶段、付款与库存交互的具体入口，在仍能取得真实 interaction／resolver 时补来源和角色。对于延迟结算或只有原生通知的路径，保留不可归因状态。不要通过时间相邻猜父事件。

### 5. 部分通知的生活含义被放大

- 唯一的 `aspiration.stage_completed` 是日志 424 的 `whimSet_VisibleSkillHigh`。EA 的 AspirationTracker 完成入口处理 FULL_ASPIRATION、WHIM_SET、通知、工作任务等多种类型，不能都称为玩家抱负阶段。12 条目标通知中也有看新闻等 utility 目标。需要资源子类型和用途分层。
- 日志 16164 的 old_mood、new_mood 都是 Mood_Stressed。EA `_should_update_mood()` 在同一 mood 的强度变化时也会发通知，所以不能简单删除同 ID 记录，也不宜写成情绪种类切换。需分别记录 mood 与 intensity。
- 43 条 trait.added 主要是吸引力偏好和机制特征，仅凭添加通知不能判定为玩家主动选择或新性格获得；创建／初始化来源还需进一步区分。
- ItemCrafted 证明游戏发送了带制作者身份的产物通知。EA 的无人设备取物、产物完成等路径都可能发送它；例如本次水果蛋糕紧接着进入、离开访客库存，没有完整做饭动作证据，不能写成“观察到访客在地块做了蛋糕”。

### 6. 中文解析还需要区分不同失败原因

在最终事件树内遍历 resource.name，得到 resolved 5174、rule_resolved 243、no_display_name 17118、unresolved_tokens 59 次。这些是**字段出现次数**，包含 facts、cause、metadata 中的重复项，不能作为翻译成功率。

59 次未解析 token 可归为：聊天内部交互 44 次、上述错误广播对象 13 次、年龄条件表达式 `{T0.…}{DAE0.…}` 2 次。前两类应先修类型／token 来源；最后一类需根据游戏年龄条件语法核验后扩展解析。

另有 26 个隐藏情绪 Buff 增减事件，其字符串表结果是空文本（在重复字段中出现 52 次），却被标为 resolved。展示器对空 text 退回到整个字典展开，把 hash、token 和名字前缀都塞进正文。应保留“有字符串键但文本为空”的诊断，正文用原始资源名兜底。

### 7. 入口健康状态没有随运行落盘

运行时 API 暴露了每个事件源的安装状态，但本次 session_start、session_end、Context 导出都没有保存完整 `event_coverage`。因此对于没有事件的职业、出生／死亡、Sentiment 等领域，现有文件不能区分“这局没发生”和“对应 Hook 不可用”。

建议在会话开始、结束保存各源 installed/unavailable、动态子类数量、错误和回调计数，并增加低开销耗时统计。这样下一局才能更有依据地判断缺口与性能。

## 下一轮建议与验收

建议先做一轮“数据含义与历史可读性修正”，继续使用 0.6.0：

1. 修资源／实体类型、情绪和配方名称入口、空字符串兜底，以及效果主语角色。用本次事件形成脱敏的回归样例。
2. 建立已确认技术计数器、内部交互和 Buff 的用途分层。用本次导出时点重放，确认主要历史能优先看到具体生活动作；未知条目依然可查询。
3. 补制作、付款、库存入口的可核实关联；不能关联的明确保留未知。检查按物件和按 Sim 查询能否找到相同事实。
4. 将入口健康与回调统计写入日志，然后再用后续游戏验证职业、人生节点、情感印象、拆堆等尚无样本的分支。

本次只完成研究和文档更新。上述问题未在本次修复，当前安装包仍为已测试的这一构建；原始运行数据保持不变。没有提交、推送或合并。
